# FPCAnalysis

Guidance for Claude Code when working in this repository.

## What this is

A scientific Python library for Field-Particle Correlation (FPC) analysis of
plasma physics PIC/hybrid-PIC/DG simulation output (Tristan, dHybridR, Gkeyll).
It loads particle and field data from simulation codes into common dict-based
data structures, then computes velocity-space correlations between particles
and electromagnetic fields to measure energy transfer. See `README.md` and
`docs/` (especially `docs/load.md`, `docs/FPC.md`) for the physics and data
model; read those before changing loader or `fpc.py` semantics.

## Current effort: scaling to larger particle datasets

We are optimizing this codebase to handle substantially larger particle counts
(target: 10-100x current typical dataset size) without changing any numerical
output. The plan lives at `docs/optimization_plan.md` — read it before picking
up any optimization task, and update its checklist as phases complete.

**The core constraint driving this work:** the current bottleneck is not CPU,
it's that particle loaders read an entire simulation frame into RAM before any
spatial filtering happens (see `data_tristan.py:load_particles`,
`data_dhybridr.py:read_particles`). Fix I/O/streaming before touching
vectorization or parallelism — a faster per-particle loop doesn't help if the
load step already OOMs.

## Project philosophy (from `docs/devnotes.md` — still applies)

> Scientific code is run once per dataset; readability and correctness matter
> more than speed in general. A measured amount of development effort should
> go to performance, not unlimited effort.

Do not let this optimization effort become a rewrite. Prefer the smallest
change that removes a genuine bottleneck. Don't introduce new abstractions,
config systems, or dependencies beyond what's needed to fix the specific I/O
and vectorization issues identified. If a fix requires non-obvious tradeoffs
(e.g., changing a public function's return type, adding a new required
dependency), stop and ask rather than deciding unilaterally.

## Key data structures (see `docs/load.md` for full detail)

- `dpar` / `dparticles`: dict of parallel 1D arrays — particle positions
  (`x1`,`x2`,`x3` or dHybridR-style), momenta (`p1`,`p2`,`p3`), charge `q`,
  frame-velocity bookkeeping key `Vframe_relative_to_sim`. Tristan data uses
  different key names (`xi`,`yi`,`zi`,`ui`,`vi`,`wi` for ions, `e`-suffixed
  for electrons) and gets renamed to dHybridR-style keys via
  `data_tristan.format_par_like_dHybridR` for compatibility with the rest of
  the library. Several functions (e.g. `fpc.compute_hist_and_cor`) do this
  key-aliasing inline too — when editing, grep for `'xi' in dpar.keys()` and
  similar before assuming a function only ever sees one key convention.
- `dfields` / `dflow` / `dden` / `dcurr`: dicts of 3D arrays ordered `(zz,yy,xx)`,
  plus 1D coordinate arrays per field per axis (e.g. `ex`, `ex_xx`, `ex_yy`,
  `ex_zz`). Field-aligned variants add `epar`/`eperp1`/`eperp2` etc.
- Everything in this library assumes particles and fields are in the same
  boosted frame; `Vframe_relative_to_sim` tracks this and multiple functions
  warn (but currently don't hard-fail) if frames look mismatched.

## Hot path (where performance work concentrates)

`fpc.py` is the core numerical engine:
- `compute_hist_and_cor` → `compute_cprime_hist` → `compute_cprimew` (numba
  `@jit(nopython=True)`, per-particle loop) → `weighted_field_average` /
  `_weighted_field_average` (trilinear interpolation, also JIT'd).
- `comp_cor_over_x_multithread` is the `ProcessPoolExecutor`-based driver used
  for large sweeps; it expects **presliced** particle data on disk (one file
  per x-slice, produced by `scripts/preslicedataTristan.py` /
  `scripts/preslicedatadHybridR.py`) and loads slices via
  `data_dhybridr.get_dpar_from_bounds`.
- Anything touched here must preserve bit-for-bit (or float-tolerance)
  equivalent output — this is the numerically load-bearing part of the
  library and has essentially no automated correctness coverage today (see
  Testing below).

## Testing — read before changing numerics

`tests/testload.py` and `tests/testframetransform.py` check loader
shape/sanity, not FPC numerical correctness. "Regression testing"
historically meant re-running the example notebooks in `notebooks/` by hand.
As of Phase 0 of `docs/optimization_plan.md`, there is now a real golden-
output regression test for the `fpc.py` hot path:
`tests/test_fpc_regression.py`, checked against `tests/golden/fpc_regression_golden.npz`
(generated by `tests/generate_fpc_golden.py`). It uses deterministic
synthetic particles (`tests/_synthetic.py`) over the real field fixture
(`tests/testdata/dHybridR/M06_th45/`) because that fixture has no particle
data checked in — only fields. **Run this before and after any change to
`fpc.py`, the `data_*.py` loaders, or `analysis.py`'s basis-conversion
functions**; if output is expected to change, regenerate the golden file
deliberately and say why in the commit.

Run both of these after any change in this area — they are not the same
invocation (pytest's default discovery pattern doesn't match the older
`testload.py`/`testframetransform.py` filenames, a pre-existing gap, not one
introduced here):
```
FPCAnalysisenv/bin/python -m pytest tests/
FPCAnalysisenv/bin/python tests/testload.py
FPCAnalysisenv/bin/python tests/testframetransform.py
```

Three benchmark scripts exist under `scripts/`, each answering a different
question — use the right one rather than re-deriving its answer by hand:
- `bench_fpc.py`: particle load + `compute_hist_and_cor` at a few synthetic
  particle-count scales, isolated per-scale peak-RSS measurement.
- `bench_sweep_redundancy.py`: profiles a *real* `compute_correlation_over_x`
  sweep (not a single isolated call) to decompose time into per-call
  filtering overhead vs. JIT compute vs. histogram binning, across slice
  counts. Built because `bench_fpc.py` alone was misleading about where time
  actually goes in a realistic multi-slice sweep — see
  `docs/optimization_plan.md`'s "Phase 0 addendum" for why and what it found.
- `bench_io_full_vs_filtered.py`: compares `data_dhybridr.read_particles`
  (full-load) against `data_dhybridr.read_box_of_particles` (bounds-filtered)
  on the same on-disk file, to isolate the actual I/O/RAM-ceiling question
  from compute cost.

Read `docs/optimization_plan.md`'s "Phase 0 addendum" section before
assuming you know which of these to reach for, or before re-benchmarking
something these three already measured.

## Environment

- Python 3.11, dependencies pinned in `requirements.txt` / `environment.yml`.
  Already includes `numba`, `h5py`, `scipy`, `numpy`; no `dask`/`joblib`/GPU
  libs currently — adding a new dependency for this effort should be a
  deliberate, flagged decision, not a default.
- Set up via `./install.py` into a local `FPCAnalysisenv` conda env (see
  `README.md`). On this machine that required installing Miniforge first
  (`brew install --cask miniforge`) since no conda was present. The library
  is installed in editable mode — changes to `FPCAnalysis/` take effect
  without reinstalling, but Jupyter kernels need `importlib.reload(...)` or
  a restart to pick up changes. Use `FPCAnalysisenv/bin/python` directly for
  one-off commands/scripts rather than relying on shell activation
  persisting (it won't, across separate tool invocations).

## Conventions already in the code worth preserving

- Loader functions always attach `Vframe_relative_to_sim` and (for particles)
  `q` to returned dicts — keep doing this for any new/modified loader so
  downstream frame-transform code keeps working.
- Spatial filtering convention is inclusive bounds via boolean masks:
  `(x1 <= dpar['x1']) & (dpar['x1'] <= x2) & ...` — match this exactly when
  adding filtered/streaming load paths so slice boundaries don't shift.
- `print()`-based progress logging is the existing convention for long-running
  sweeps (not a logging framework) — match it rather than introducing logging
  infra, unless asked.
